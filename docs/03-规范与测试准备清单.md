## 2. 第一批可以推进的模块

### 2.1 背包负重倍率（建议首先完成）

范围只包含“已占格数→速度倍率”；物品拾取、堆叠、装备和移动控制另属模块。

已确认规则：默认容量10格，倍率为1.2−0.03×已占格数。

| 已占格数 | 预期倍率 |
|---|---|
| 0 | 1.20 |
| 1 | 1.17 |
| 2 | 1.14 |
| 3 | 1.11 |
| 4 | 1.08 |
| 5 | 1.05 |
| 6 | 1.02 |
| 7 | 0.99 |
| 8 | 0.96 |
| 9 | 0.93 |
| 10 | 0.90 |

需要先在模块README固定的工程契约：输入采用整数；负数和超过容量的输入建议显式拒绝，不静默截断；倍率表示精度与比较方式明确。上述错误处理是工程建议，尚未成为现有接口。

测试还应验证相同输入结果一致、每增加一格减少0.03、结果处于0.9至1.2之间。不需要先决定每件财宝占几格，也不需要等待最终角色模型。

### 2.2 探险时钟

已确认规则：06:00开始，现实1秒推进游戏1分钟；加载不计时，全体出发成员加载完成并统一到达后开始，无落地安全期。

首批预期结果：

- 启动时显示06:00；经过1现实秒显示06:01。
- 启动后720现实秒对应18:00；1080现实秒对应次日00:00。
- 出发动画和加载等待不会减少探险可用时间。
- 测试通过虚拟时间推进至边界，不实际等待12或18分钟。

需要先固定：未启动状态的输出、亚秒精度、重复启动处理、截止事件只触发一次的契约。显示时间与截止判定应分开测试，不能靠显示取整决定失败。

注意：12分钟到18:00、18分钟到午夜是现有规则的数学推导；“12分钟作为建议游玩时长”的产品解释仍待确认。不能擅自写成12分钟强制结束。

### 2.3 队伍容量与到达屏障

可确定的行为：允许1、2、3、4人出发；不允许0人或5人。所有出发成员完成加载、统一到达前不启动探险。

需要补齐：出发成员名单何时冻结、重复加载回执如何处理、陌生玩家回执如何拒绝，以及加载超时/中途断线后的取消或继续策略。先完成容量规则；屏障的异常分支待契约明确后测试。

## 3. 会阻塞后续模块的玩法缺口

| 优先级 | 模块 | 缺失的确定规则 | 不确定时无法验证什么 |
|---|---|---|---|
| 下一步 | 搬运 | 每件财宝占格数、堆叠、消耗品是否占财宝格、装车交互 | 满包拾取、卸货、道具使用及速度更新 |
| 下一步 | 撤离 | 即时发令还是持续读条；有效马车范围；受控能否发令；截止瞬间处理顺序 | 发令是否成功、谁上车、午夜与死亡竞态 |
| 下一步 | 结算 | 装车但失败的财宝；随身未卸货财宝；队内分配；死者是否分红 | 成败资产的精确增减 |
| 下一步 | 战斗 | 系数如何换算血量和攻击；装备贡献；攻击间隔、有效距离及命中判定 | 三击击杀、一击必杀、重复伤害与武器行为 |
| 地图模块前 | 随机地图 | 模块尺寸与接口、通行净空、楼梯坡度、地图规模、连通性要求、生成失败处理 | 地图是否可达、能否返回马车、种子重现与客户端一致性 |
| AI模块前 | 感知 | 视角、视野/距离/遮挡、声音来源与传播、静止阈值、凝视是否连续 | 看见、听见、注视及丢失目标的精确条件 |
| AI模块前 | 特殊怪物 | 机制时间单位、史莱姆分裂下限、救援误伤和致死时限、幽影确认看见、蜘蛛追踪规则 | 救援与死亡、分裂是否可终止、四次显现是否触发 |
| 联机生命周期前 | 断线与死亡 | 重连时限、断线角色留场、死亡掉落、全灭结束、技术故障退款 | 掉线不能复制资产或回避死亡，失败恢复一致 |

战斗尤其需要先解决：现有H=30s、A=10s只是建议；按该建议，部分强怪会一击杀死顶装玩家，史莱姆初始血量也高于顶装单次攻击。这些不能在测试中悄悄固化。

## 4. 测试设施还需定义的边界

- 纯规则测试：无需模型、联网或真实等待，覆盖计算及状态转换。
- 契约与集成测试：重复消息、并发拾取、重复结算、乱序与重连；替身通过不等于真实联机通过。
- 引擎测试：碰撞、视线遮挡、坡道导航、模块拼接；需要简单的真实3D测试场景。
- 微信真机测试：加载、内存、帧率、触控和切后台恢复；需明确目标设备与验收阈值。现有性能预算仍是候选值。

需要少量测试素材：房间、走廊、楼梯、坡道、遮挡墙、角色碰撞体及财宝占位物；每种形状有固定尺寸。它们服务于规则验证，正式美术可以后续替换。

引擎版本、测试框架及命令由工程兼容性验证决定；尚未验证前不填造假的运行命令或通过记录。
