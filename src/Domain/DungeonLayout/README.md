# DungeonLayout：三维模块布局核心

## 用途与边界

实现服务端可调用的纯C#地图核心：候选门位对接、三维占用检查、门口净空、有限回退生成和独立最终校验。用户已授权预设房间并实现；本批参数是技术原型，不是正式美术或玩法定稿。

编排模块调用本模块；客户端消费布局。引擎预制件加载、真实碰撞/导航、联网、门交互、财宝和刷怪不在本模块内。占用检查成立的前提是未来素材的实体结构被声明包围盒覆盖。

## 必须遵守的规范

| ID | 规范 |
|---|---|
| MAP-001 | 单位0.5米，Y向上；只允许绕Y旋转0/90/180/270度。正向90度将(x,y,z)变为(z,y,-x)。几何判断使用整数 |
| MAP-002 | 模块由正体积AABB集合和候选门位组成；门洞整个内侧属于模块、外侧为空；目录和门位ID唯一 |
| MAP-003 | 门位基准为门洞底边中心；对接时坐标重合、朝向相反、宽高和类型相同，由门位反推房间变换 |
| MAP-004 | 不同实例的盒不能有正体积交集，包括相互连接的房间；允许接触。逐盒检查，L形空缺不是实体 |
| MAP-005 | 已连接门口两侧各保留1米净空，宽高取门洞尺寸；第三方实例不得侵入。未连接门位默认封墙 |
| MAP-006 | 独立校验实例/连接ID、引用、门位唯一使用、对齐、尺寸、三维占用、门口净空及从入口的图可达性 |
| MAP-007 | 随机候选顺序、逐步放置与回退；严格限制尝试次数，失败不返回半张地图。默认保留树形模式；请求环路时先用指定连接模块生长环路骨架，再扩展其他房间；不允许远距离虚拟连接 |
| MAP-008 | 随机源注入；XorShift32固定算法，0种子映射为0x9E3779B9；相同目录、种子和请求在本版本内可复现 |
| MAP-009 | 可要求至少两个不同高度的已连接门口；楼梯包络高不等于已形成跨层路线。实例1～64，尝试预算1～100000 |
| MAP-011 | minimumCycles为0～8；环路模式必须提供cycleModuleId。闭环只连接未使用、同位置、相向且尺寸类型相同的门；既有最短路线至少3条边，新增门形成至少4房间环。成功必须满足独立环路数E−V+1≥minimumCycles，否则失败，不降级成树 |
| MAP-012 | 每次放置和尝试闭环都计入共享预算；闭环后仍做完整几何校验。优先放置能闭环的候选；未达到环路目标时仅使用指定连接模块。环路模式要求跨层时，最后两个名额优先建立不同高度的连接，最后一个名额排除不可能完成高差的候选。回退须同时撤销该房间及其新增连接 |
| MAP-010 | 只读布局包含版本、实例变换和连接；每条连接一个门实体ID；不包含怪物、财宝或其他私有游戏状态 |

## 原型房间参数

尺寸单位米，顺序X×Z×Y，原点位于底层平面中心（L形为外框中心）。占用是结构预留外包络，不是室内净尺寸；墙体向内制作，避免接缝外扩。门洞统一宽2米、高3米，连接类型standard。

| 模块ID | 名称 | 占用尺寸 | 候选门位 | 说明 |
|---|---|---|---|---|
| entry | 入口房 | 8×8×4 | 北2、东1、南1、西1 | 只作根房间 |
| hall | 大厅 | 12×10×4 | 北2、东2、南2、西2 | 出入口组合随机 |
| corridor | 直走廊 | 3×8×4 | 北1、南1 | 门口居中 |
| elbow | L形房 | 外框8×8×4，两个盒组合 | 北1、东1、南1、西1 | 东北4×4米空缺 |
| stairs | 楼梯间 | 4×10×8 | 南底层、北高4米 | 实际台阶及导航后续验证 |
| ramp | 坡道间 | 4×16×8 | 南底层、北高4米 | 高差4米；实际通行性后续验证 |

参数唯一来源为PrototypeCatalog.Create。示例由实际C#生成器导出，交互预览只渲染结果，不另写生成算法。

## 接口与依赖

- GridPoint/GridBox：整数坐标与正体积盒；DoorSocket：ID、底边中心、方向、宽、高、类型。
- RoomDefinition/RoomCatalog：只读目录与内容版本。局部坐标限±256格；门宽是1～128格内的正偶数，高1～128格；拒绝缺失体积、重复ID或非法门洞。
- PlacedRoom：实例ID、模块ID、位置、旋转编号。世界位置限±1000000格；旋转0～3，变换溢出必须拒绝。
- DoorConnection：连接ID、两端实例/门位ID、唯一门实体ID；DungeonManifest：生成器/内容版本、实例和连接。
- LayoutGeometry.Attach：计算新实例的变换；LayoutValidator.Validate：返回错误码集合，空集合才合法。
- DungeonGenerator.Generate：目录、根模块ID、目标数量、随机源、尝试预算、跨层要求；返回布局或失败原因、尝试与回退次数。
- 非法参数抛ArgumentException或派生类型；随机源返回越界值抛InvalidOperationException。预算耗尽返回失败结果，不抛异常、不返回部分布局。输入集合复制为只读集合。

只允许标准库，不读取文件、不调用引擎、网络或真实时钟。JSON适配器属于后续协议层，本次测试导出是可检查的样例，不声称已经实现传输协议。

不能随意打洞，不能忽略相连房间的重叠；不改变不可破坏地形，不添加财宝或门锁玩法。参数变更先更新规范和测试，实际素材还须验证包络、通行净空和NavMesh。

## 环路扩展 v0.2

原目录Create保留；CreateLoopReady在其基础上增加junction：8×8×4米，四面中心各一个2×3米门洞。用于本批预览，不代表全部正式房间必须等大。

Generate增加minimumCycles（默认0）和cycleModuleId（默认null）；本批预览请求18房间、至少2独立环路、跨层连接，cycleModuleId="junction"。先形成可回绕骨架，保留房间余量扩展大厅、走廊、楼梯及死路。不保证环路跨层，也不等同于已验证玩家一定迷路；环路大小、岔路分布、视线和地标仍需游玩测试。

LoopConnections.Find返回已有合法布局中可实际闭合且至少4房间的候选门连接；不移动已有房间、不放宽碰撞。候选应用后必须再次验证，不保证所有候选可同时使用。生成器版本更新为socket-graph-v0.2；旧样例仍保留其原版本。

MAP-011/012由DungeonLoopTests覆盖：矩形真闭环、拒绝远程连接/两房间双门/已占用门，共享预算、不可满足环路无部分输出、确定性、跨层与批量种子输出。

环路扩展实际验证：新增10个用例全部通过，原50个地图用例未放宽；100种子均满足18房间、2环路、至少两种已连接门高度，最高39次尝试。先行Red及最终102规则+14规范检查报告见evidence/public-loops。交互预览依据测试导出数据，脚本语法已检查；浏览器视觉实测仍受此前本地安全策略限制。

## 长支线末端连接 v0.3

用户否定优先闭合最近门位所形成的四房间小环。新主预览改用BranchLoopGenerator：先确定分叉点，生成两条自避让支线，再在空闲网格中搜索连接两端的实体模块路径。原局部环模式保留为兼容接口，不作为新预览的实现。

| ID | 规范 |
|---|---|
| MAP-013 | BranchLoopGenerator的每个环必须有两个独立支线，从同一分叉点各延伸至少4个房间；连接前两端均为叶节点。连接段至少包含2个新房间，不以近邻开门替代远端连接 |
| MAP-014 | 路径规划使用8米网格和四向连接房，支线长度4～6随机。只占用空闲单元；连接段通过有界BFS寻找，逐模块生成真实门连接，最终仍执行三维几何及图校验 |
| MAP-015 | 输出生成轨迹BranchLoopTrace：分叉、两支线房间ID、连接段房间ID、闭环连接ID；每个环至少11房间，删除其闭环边后两端仍有至少10条边的替代路径，不允许后续生成短路破坏该约束 |
| MAP-016 | 随机源注入、预算1～100000，路径候选、BFS扩展、实际放置与闭环共用预算；无法完成返回失败且无部分地图/轨迹。完成骨架后只扩展树形支路；预览40房间、2个大环，要求跨层连接 |

BranchLoopGenerator.Generate使用本原型目录（entry+junction为8米网格，junction四面中心门），不声称支持任意形状的自动走廊路由。连接段目前由连接房灰盒组成；窄走廊、复杂形状、跨层桥接与正式美术是后续工作。

DungeonGenerator.Generate新增可选initialLayout，验证已有清单后继续扩展到目标房间数；非法、版本不匹配、根模块不匹配或超过目标数量的输入必须拒绝。用于保持长环骨架，再补其他模块和跨层支路。

新测试类DungeonBranchLoopTests验证MAP-013～016：两支线深度与叶端、连接段长度与真实对齐、整体最短环长、无部分失败、种子确定性及100种子导出。先运行编译桩有效Red，再实现。

长支线模式最新验证：新增8个用例（含两个已有清单扩展用例）通过，原断言不变；100种子均为40房间、两个大环、跨层支路，全图没有短于11房间的环。最高8374次尝试，预算10000，不能推导所有种子均成功。分叉规划失败会重新尝试，Backtracks合计规划重试与末尾扩展回退。预览种子1的两个环均为18房间，连接段分别8与9房间；前6种子样例环长14～22房间。

API界限：targetRooms为1～64，loopCount为1～4；目标过小或空间预算不足返回无部分结果的失败。BFS边界为已有占用外框各扩4格，失败允许重试新支线规划。扩展清单时保留原ID，新ID避开已有实例、连接及门实体ID。当前连接段使用8米连接房灰盒，不是最终窄走廊素材；跨层仅在后续支路，跨层长环未实现。

最新证据：evidence/public-branches；110规则+14规范检查通过。预览脚本语法通过，浏览器视觉实测仍受此前安全策略限制；引擎、真实导航和微信真机未验证。

## 种子决定大环数量 v1

| ID | 规范 |
|---|---|
| MAP-017 | SeededDungeon.Resolve(uint worldSeed)确定性导出LoopCount（1～4）和LayoutSeed；环数与布局使用不同盐值的独立派生，后续布局消耗随机数不得改变环数。禁止使用运行时GetHashCode、真实时间或共享全局随机源 |
| MAP-018 | 当前原型规则seed-rules-v1：环数1/2/3/4分别配置24/40/56/64个房间，保留已接受的长支线规则与跨层要求。此规模映射为技术验证默认值，不是最终难度、时长或微信性能定稿 |
| MAP-019 | Generate记录原始种子、规则版本、派生环数、房间数、布局种子及实际成功的尝试序号/种子。最多5次确定性布局尝试，每次最多20000步，共享总预算（默认100000）；重试只能改变布局种子，不能改变环数/房间数。失败不返回部分布局；同种子、版本、预算得到同结果 |

固定算法：Mix(x)依次执行x ^= x >> 16；x *= 0x7FEB352D；x ^= x >> 15；x *= 0x846CA68B；x ^= x >> 16，乘法按uint溢出截断。LoopCount = 1 + (Mix(worldSeed ^ 0x4C4F4F50) & 3)，LayoutSeed = Mix(worldSeed ^ 0x4C41594F)。第0次使用LayoutSeed，第i次(i=1～4)使用Mix(LayoutSeed ^ (uint)i * 0x9E3779B9)。种子0合法。

SeededDungeon是推荐的自动入口；显式loopCount接口保留给测试和设计调参。服务端未来应记录完整Plan及实际清单，客户端仍按服务器清单搭建，不自行抽取环数。未来修改概率、房间数映射或派生算法须升级RuleVersion。


调用示例：

```csharp
var result = SeededDungeon.Generate(worldSeed: 86);
// result.Plan包含确定的环数、房间数、原始/布局种子与规则版本。
// 成功布局位于result.Result.Layout.Manifest；服务端必须先检查Succeeded。
```

规则复现需同时固定RuleVersion、目录/生成器版本和maxAttempts；日志应保存调用预算与返回的Plan、AttemptIndex、ActualLayoutSeed及最终清单。总预算用尽返回BudgetExceeded，5种布局尝试均失败且尚有预算时返回LayoutVariantsExhausted。显式参数入口仍可用于设计测试，不改变自动入口规则。

最新验证：新增15用例先全部有效Red，后全部通过。种子0～99分别生成1/2/3/4环24/24/26/26次；种子86在布局变体1成功，始终保持3环，总工作量最高20235步。每张结果复用长支线全图最短环检查，无四房间捷径。125规则+14规范检查通过，0跳过。证据见evidence/public-seeds。现有40房间双环预览保留作结构示例，不代表自动入口仍固定双环。

## 独立探索支路与预算 v0.4 / seed-rules-v2

用户已授权修复大环耗尽空间的问题。默认种子规则升级v2，旧v1可显式选择；同版本、目录、生成配置仍可复现。原型地图规模随1/2/3/4环改为32/56/80/104房间，新增模式最多128房间；旧显式接口未开启支路配置时仍限64房间。

| ID | 规范 |
|---|---|
| MAP-020 | 每环指定数量的独立探索支路，原型默认2条；每条随机2～4房间。各支路从对应大环不同房间出发，支路房间不属于任何大环且互不复用。出口只连回原锚点，末端度数1，不计入口 |
| MAP-021 | 在大环生成前抽取全部支路深度，预留它们的实际房间总数，再留跨层空间与未生成大环最小用量；不能让大环消耗该预算。生成结束必须完整拥有指定支路，否则返回失败、不返回部分布局和轨迹 |
| MAP-022 | ExplorationBranchTrace包含LoopIndex、AnchorRoom、Rooms有序链。最终每条内部节点度数2、末端度数1，锚点在指定环且至少3路；树形补充禁止从受保护的支路房间继续扩展，不能吞掉死路或缩短其深度 |
| MAP-023 | SeededDungeon.Resolve/Generate可指定ruleVersion，默认seed-rules-v2，保留seed-rules-v1。v2的Plan披露每环支路数、最小/最大深度和新房间数；环数和LayoutSeed派生算法不变。成功/失败/重试仍共用原预算，重试不得降低支路要求 |

ExplorationBranchOptions(branchesPerLoop=2,minDepth=2,maxDepth=4)：每环1～4条，深度1～8且min≤max；非法值拒绝。BranchLoopGenerator.Generate新增可选exploration，null保留旧行为；显式选项激活128房间上限。低层DungeonGenerator允许显式maxRoomCount（1～128，默认64）和protectedRoomIds，验证受保护ID属于初始布局。所有实际占用/门口/长环/连通检查保持。

房间数是技术验证配置，不代表最终探索时长或微信内存预算已确定。新模式使用exploration-branches-v0.4清单版本，旧模式保持branch-routing-v0.3。新测试类DungeonExplorationBranchTests覆盖MAP-020～023：预算不足、支路深度及隔离、度数保护、环上分布、种子版本兼容、100种子全图和失败无部分结果。

验证结果：新增17个用例通过，包含100个种子的最终支路链、环上锚点、无短环、空间占用、连通和跨层验收；最高20690次尝试，未降低100000总预算。最终142规则+14规范检查通过，0跳过。旧版15个种子测试显式选择v1，原断言保持。种子5在v2中104房间、4环（20/14/14/24房间）、8条保障支路（深度2/3/2/3/4/4/3/4），额外填充后共13个非入口死路、19处分叉。支路总数可以多于保障数量。证据见evidence/public-exploration，实际清单见docs/examples/exploration-layouts.json。
